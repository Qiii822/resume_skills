# 经历匹配打分 · 常见误区

> Step 2 打相关度（高 / 中 / 低）时查阅。核心原则：先看「能力维度」是否重合，再看「量级 / 深度」是否匹配；
> 只靠关键词字面命中会误判。

## 容易「高估」相关度的情况

1. **做过类似功能 ≠ 具备同等深度**
   示例：某项目里用了一次 Redis 缓存，被当成"有高并发 / 缓存优化经验"。
   实际：JD 要的是系统性性能优化能力，单次使用 ≠ 深度经验，应降为中或低。

2. **技术栈同名 ≠ 能力匹配**
   示例：课程项目用过 Java，被当成"Java 生产级开发经验"。
   实际：未经生产环境、规模、协作检验的技能，相关度应下调。

3. **"负责 / 主导"字样 ≠ 真实责任量级**
   示例：简历写"负责 XX 模块"，但实际是照着搭好的框架填业务逻辑。
   实际：JD 的"主导 / 从 0 到 1"要求真实 owner 责任，自述词与责任量级不符时不能据此升为高。

4. **行业相同 ≠ 岗位相关**
   示例：都是互联网公司，但用户做的是运营，JD 招的是底层开发。
   实际：行业一致性是弱信号，岗位职责 / 能力维度才决定相关度。

5. **久远且未再使用的技能**
   示例：两年前用 Python 写过脚本，之后再没用过，JD 要 Python 主力开发。
   实际：长期未维护的技能应降级，除非有持续使用的证据。

## 容易「低估」相关度的情况

1. **可迁移的软性能力被忽略**
   示例：用户"跨 3 个团队推动上线"，JD 强调"跨团队协作、owner 意识"。
   实际：这类过程性能力即使不含具体技术名词，相关度也很高。

2. **非本岗位直接经历，但有方法论迁移价值**
   示例：用户做过数据分析，投产品岗；JD 要"数据驱动决策"。
   实际：底层方法（拆解问题、用数据验证）可迁移，不应直接判低。

3. **项目规模小但"闭环完整"**
   示例：独立走完"设计 → 实现 → 上线"的小项目，用户量不大。
   实际：JD 若看重 owner 意识 / 从 0 到 1，闭环完整比规模更能证明相关度。

4. **教学 / 竞赛 / 开源贡献被当成"无产出"**
   示例：开源项目被合并 PR、竞赛获奖、给几十人讲过课。
   实际：这些都是可量化的成果，与"影响力 / 主动性"维度高度相关。

5. **用词不匹配 JD，但底层能力一致**
   示例：用户写"搭了个网站"，JD 要"Web 全栈开发"。
   实际：这是同义能力，重写时对齐术语即可，不应因字面不匹配而误判低。

## 操作建议

- 先列「能力维度」清单（技术栈、职责类型、结果性质、软性能力），再逐段经历对号入座。
- 字面命中只是起点；量级、深度、时效、可迁移性才是决定高 / 中 / 低的依据。
- 拿不准时：宁可在「定制说明」里标出"建议用户核实这段经历的深度"，也不要把相关度擅自拔高。
