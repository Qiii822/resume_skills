# Resume Tailor（定制化简历生成）

根据用户提供的个人资料与目标岗位 JD，生成一份高度定制化的简历 Markdown。
输出为 Markdown（**不生成 PDF**），方便用户后续手动修改与自行转换格式。

> **可移植性**：本 Skill 遵循开放的 Agent Skills 格式（`SKILL.md` + frontmatter），
> 不绑定 Claude Code；任何支持该格式的 agent 均可加载。本 Skill 对宿主环境仅有一项能力要求：
> **联网搜索**（用于 Step 1 检索公司信息，可用任意 web search 工具实现）。若宿主无联网能力，
> 则跳过检索、明确标注文化判断仅基于 JD 措辞与用户提供的资料。

## 适用场景

- 用户手头已有一份"通用简历"，需要针对某个具体岗位重写、突出匹配点
- 用户提供个人资料 + 目标岗位 JD，希望从零生成定制简历
- 用户想了解"我的哪些经历和这个岗位相关、哪些该舍弃、哪些需要补数据"

## 输入要求

开始前，确认用户已提供以下三样（缺一不可，否则按"禁止事项"先追问）：

1. **个人资料（profile）**：建议用户先按 `profile-template.md` 填写并保存为 `profile.md`，后续复用。
   至少包含：基本信息、教育背景、实习/项目经历、技能清单、证书。
2. **目标岗位 JD**：完整 JD 原文（或关键段落）。
3. **招聘公司**：公司名（用于判断文化倾向、检索补充信息）。
   可选：用户已知的公司文化 / 招聘偏好 / 面试官风格。

**语言判断**：
- 以用户提供的 profile **主体语言**为准（中文材料 → 中文简历，英文材料 → 英文简历）。
- profile **中英混用**时：以内容占比最高的语言为输出语言；JD 中的专有术语（技术名词、职级、产品名）
  保留原语言、不翻译；若仍无法判断或用户偏好不明确，**追问用户**。
- 用户明确指定输出语言时，以用户指定为准。

## 工作流程（严格分步执行，不得跳步）

### Step 1 — JD 拆解

- 提取**硬性技能要求**，并区分「必须项」与「加分项」（must-have vs nice-to-have）。
  区分依据：措辞强度——"必须 / 要求 / 精通" → 必须项；"优先 / 加分 / 熟悉为佳 / 了解" → 加分项。
- 提取**核心职责关键词**：显式名词（技术栈）+ 职责动词（"优化 / 从 0 到 1 / 主导 / 推动"）+ 软性要求（协作、owner、抗压）。
  JD 中重复出现 ≥2 次的词通常是最核心的信号，优先提取。反模式见 `reference/jd-extraction-anti-patterns.md`。
- 从 JD 的**措辞风格反推团队文化倾向**，例如：
  - 大量"闭环、owner、从 0 到 1、扛事" → 偏结果导向 / 创业互联网风格
  - 大量"协作、赋能、对齐、流程、规范" → 偏大公司 / 正式规范
  - 强调"稳定、服从、公文式表述" → 偏国企 / 事业单位
- **补充检索**（仅当用户没提供文化/偏好信息时）：用 web search 检索该公司官网、近期新闻、
  员工评价（招聘平台 / 匿名社区）、同类岗位历史 JD。
  - **最低期待**：能返回公司官网 / 新闻标题即可，凭标题与 URL 判断基本定位与调性；
    能返回正文（about us / 招聘页 / 员工评价摘要）更佳。
  - **失败降级**：若搜索无结果、结果无意义或无法访问，**不要硬编**，按「仅基于 JD 措辞推断」处理。
- **文化依据标注约定**（Step 5 定制说明中必须标注来源）：
  - `[用户提供]`：来自用户原话
  - `[web search]`：来自检索到的公司官网 / 新闻 / 员工评价
  - `[基于 JD 推断]`：仅从 JD 措辞反推
  - `[未检索到有效信息，仅基于 JD]`：检索失败后的降级标注

### Step 2 — 经历匹配打分

- 把用户提供的**每一段经历**与 JD 逐条比对，给出相关度评级：**高 / 中 / 低**。
- **只保留「中」及以上相关度的经历**；低相关度经历直接舍弃，不要为填满篇幅硬塞。
- 打分先看「能力维度」是否重合（技术栈、职责类型、结果性质），再看「量级 / 深度」是否匹配；
  只靠关键词字面命中会误判，具体误区见 `reference/scoring-pitfalls.md`。
- **信息缺失的处理（三档，按严重程度）**：
  1. 缺失的是 JD「必须项」对应的技能 / 经历（如 JD 要 Go，用户完全没有相关经历）→ **停下追问**，不硬凑、不虚构。
  2. 缺失的是某段经历**整段的"具体做了什么 / 结果"** → **停下追问**（对应禁止事项第 4 条）。
  3. 仅缺失某段经历的**量化数字**（成果真实存在但没写数）→ 用占位符 `[需补：具体数字]` 写入正文，
     并在 Step 5 定制说明里列成「待补充清单」，**其余内容照常生成**。**禁止编造**具体数字、项目名、公司名。

### Step 3 — 语言重写

- 用 **STAR（Situation-Task-Action-Result）** 或 **CAR（Context-Action-Result）** 逻辑重写每条经历。
- **"一句话" = 一条要点 = 一个完整 STAR/CAR 闭环**，而非硬性字数 / 词数限制：
  - 中文：一个句号收束的一句话（内部可用逗号分句）。
  - 英文：一个完整句子（可含从句）。
  - 目标是把"做了什么 + 用什么 + 达到什么结果"压进一条要点，但不以牺牲关键信息（技术栈、你的具体动作）为代价。
- **过度精简防护**：若用户某段经历本身已是 STAR/CAR、信息完整、语气合适，**只做对齐 JD 术语的微调**，
  不必为"重写"而重写；不强行把两行有信息量的内容砍成一行导致丢信息。
- 术语向 JD 原文的表述**靠拢**——前提是语义确实一致；不能强行替换成不相关、用户不具备的说法。
- 根据 Step 1 判断的公司文化调整语气，参见 `reference/style-guide.md`：
  - 大厂/外企 → 正式规范
  - 创业公司/互联网公司 → 结果导向、突出主动性与 owner 心态

### Step 4 — 篇幅控制

- 目标压缩到 **1 页**，最多不超过 **2 页**。
- 输出为 Markdown，无法直接控制字号，因此改用**内容密度控制**：
  - 内容多 → 每条经历压缩成一行短句
  - 内容少 → 适当展开到两行
- **页数估算方法**（仅用于末尾那一行结论，不在正文写字号）：
  - 按常见单栏 A4 简历模板、正文约 10.5–12pt、行距约 1.15–1.5 估算；
  - 经验换算：联系人 / 标题 ≈ 3 行，教育每段 ≈ 2–3 行，每条经历要点 ≈ 1–2 行，技能 / 证书 ≈ 3–6 行；
  - 累计约 **45–55 行 ≈ 1 页**，90–110 行 ≈ 2 页。
- 在文档**末尾用一行**注明"当前内容量预计对应约 X 页"。
- **不要**在正文里出现具体字号数值之类的伪造排版指令。

### Step 5 — 输出

生成两部分：

1. **完整简历 Markdown 正文**（符合简历常规结构：个人信息、教育背景、经历、技能、证书等）。
   缺失量化数字处用 `[需补：具体数字]` 占位。
2. **正文之后追加一个 `# 定制说明` 区块**，至少交代：
   - 这次做了哪些取舍：**保留了什么、舍弃了什么、为什么**（对应 Step 2 的评级结果）。
   - **待核实 / 待补充清单**：列出所有 `[需补：…]` 占位项，以及 JD 要求但 profile 缺失的技能 / 经历。
   - 对公司文化的判断**依据来自哪里**，按 Step 1 的标注约定标注来源（`[用户提供]` / `[web search]` / `[基于 JD 推断]`）。

## 禁止事项（硬性约束，违反即失败）

- ❌ **不编造**任何用户没提供的具体数字、项目名、公司名、技能。
- ❌ **不堆砌**用户完全不具备的技能，只为匹配 JD 关键词。
- ❌ **不能省略** Step 5 的"定制说明"部分。
- ❌ **信息不全时不许假设着往下写**：每次生成前，若用户信息不全（如缺少某段实习的具体产出），
  必须先追问，得到补充后再继续。
